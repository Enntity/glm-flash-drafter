How it works and how we validate

What this network trains

A speculative-decoding drafter for GLM-5.3-Flash, trained from a fresh initialization and released under Apache-2.0. Every site trains a full copy of the drafter on its own data for a short round (about 30 minutes of training), then uploads only the difference between its weights and the global weights it started from (a delta). A validator averages accepted deltas, weighted by tokens trained, into the next global version (plain averaging; the method is DiLoCo with outer learning rate 1 and no outer momentum).

What leaves a site, and what does not

  • Uploaded: weight deltas (safetensors tensors only, never code or pickles) and their metadata: mode, recipe id or an opaque tag, token and step counts, trainer version, base hash, and a signed data-source attestation.
  • Heartbeats: phase, counters, throughput, GPU power. No hostnames, file paths or free text.
  • Never uploaded: prompts, completions, activations, or any file from the site. In bring-your-own-data mode the site's data never leaves it.

How every delta is validated

  1. Before training, the site's client compares its trainer, config and validator versions with the network's pins. At upload initiation, before any bytes move, the coordinator checks the trainer and config versions again, that the base is a retained global it published, size caps and the attestation signature.
  2. On the site, before upload: the same checks the validator runs (layout, finite values, size bounds, base hash) and a small public check set. A delta that fails locally is never uploaded.
  3. On the validator: SHA-256 of the stored file, the same checks again, an optional replay of recipe shards, then a held-out evaluation of the site's trained weights against the base on a private, rotating held-out set that is not in the repository or on this server.
  4. Conservative verdicts: a delta is accepted unless a held-out group gets worse. A small drop is borderline (merged at half weight or held for the operator); only a clear regression is rejected.
  5. Rejected deltas are quarantined, not deleted, with a machine-readable and a human reason shown to the site. When the validator is fixed, its version changes and every quarantined delta is validated again.

What we promise contributors

  • A short canary run is validated end to end before a site starts long rounds, and again after any version change.
  • Version mismatches are refused at upload initiation, never after the upload.
  • Deltas against older globals are accepted with lower weight while their base is retained, and every base a live site is training from is retained.
  • Work counts on receipt: the dashboard credits tokens as soon as a delta arrives, whatever validation later decides.
  • Uploads resume after interruption; a site keeps its delta until the coordinator has it and has given a verdict.

Trust and security

  • Joining is by one-use invite. The invite code travels in the link's fragment, which browsers never send to servers. Site tokens are stored only as hashes.
  • Administrative actions are available only on the server's loopback interface and are recorded in an audit log (registrations, invite use, accepts and rejects, revocations).
  • Weights and deltas move directly between sites and object storage through short-lived signed URLs.
  • A drafter cannot change GLM-5.3-Flash's output under greedy verification; a bad drafter can only make decoding slower, which the held-out checks are there to catch.
